# راهنمای بک‌اند دکون (Backend Brief) — پیش‌نویس ۰٫۱

> برای توسعه‌دهنده‌ی بک‌اند. همراه این فایل: `dokoon-openapi.yaml` (قرارداد API اپ مشتری) و سه سند طراحی (`dokoon-screen-specs.md` مرجع رفتار هر صفحه، `dokoon-design-system.md`، `dokoon-component-library.md`).
> وضعیت: پیش‌نویس از روی پروتوتایپ؛ هر جا «تصمیم لازم» آمده، باید قبل از کدنویسی بین شما و مالک نهایی شود. هیچ‌چیز این سند روی سرویس واقعی (درگاه، پیامک، نقشه) آزمایش نشده است.

## ۱. دامنه‌ی محصول
چهار مصرف‌کننده، یک سرور:
1. **اپ مشتری** (این قرارداد) — اندروید (APK) + PWA آیفون.
2. **اپ رستوران** — سفارش‌ها، منو، ساعت کاری، زمان تحویل (`etaMin/etaMax`)، `allowExtras`، `allowCash`.
3. **اپ پیک** — قبول سفارش، مسیر، تحویل، دریافت وجه نقد، تسویه.
4. **پنل ادمین** — وب؛ رستوران/پیک/کاربر/مالی/محتوا/کمپین/کد تخفیف/شهرها و محدوده‌ها.
فاز ۱: فقط API اپ مشتری قطعی شده؛ بخش ۹ فهرست کلی بقیه است.

## ۲. معماری پیشنهادی (قابل تغییر با نظر شما)
- API: REST + JSON (نسخه‌ی `/v1`)، OpenAPI به‌عنوان منبع حقیقت. زمان واقعی: SSE (یا WebSocket) برای وضعیت سفارش؛ جایگزین: poll هر ۱۵ ثانیه.
- دیتابیس: PostgreSQL (+ PostGIS برای محدوده‌ی سرویس و فاصله). کش/صف/محدودیت نرخ: Redis. صف کار پس‌زمینه (پیامک، پوش، تایم‌اوت سفارش، تسویه).
- فایل/عکس: ذخیره‌ی شیء (S3-سازگار داخلی)، پردازش مجدد تصویر و حذف EXIF.
- همه‌ی میزبانی و سرویس‌ها باید از داخل ایران قابل دسترس باشند (درگاه، پیامک، نقشه). تصمیم لازم: میزبانی (ابر داخلی) و دامنه.
- زبان/فریم‌ورک: به انتخاب بک‌اندکار؛ فقط قرارداد را رعایت کند.

## ۳. قراردادهای عمومی API
- پول: عدد صحیح **تومان**؛ هیچ اعشاری. قیمت نهایی همیشه از سرور؛ کلاینت فقط نمایش می‌دهد.
- شناسه‌ها رشته‌ی مات (UUID/ULID). زمان‌ها ISO-8601 UTC؛ کلاینت به تقویم/ساعت ایران تبدیل می‌کند.
- ارقام: سرور هر دو نوع رقم فارسی/عربی/انگلیسی را در ورودی نرمال می‌کند؛ خروجی همیشه ASCII.
- خطا: `{code, message(فارسی)، details}`؛ کدها: `OTP_INVALID, RATE_LIMITED, OUT_OF_ZONE, RESTAURANT_CLOSED, PRICE_CHANGED, ITEM_UNAVAILABLE, MIN_ORDER, PROMO_INVALID, CANCEL_NOT_ALLOWED, UNAUTHORIZED, FORBIDDEN, NOT_FOUND, SERVER_ERROR`. وضعیت‌های HTTP معنادار (۴۰۱ → اپ صفحه‌ی ورود؛ ۴۰۳/۴۰۴/۵۰۰/۵۰۳/۵۰۴ → صفحه‌ی خطای متناظر اپ).
- صفحه‌بندی: cursor (`nextCursor`)؛ لیست‌های بلند: رستوران‌ها، نظرات، سفارش‌ها، اعلان‌ها.
- `Idempotency-Key` اجباری برای `POST /orders` و پرداخت.
- زبان همه‌ی متن‌های کاربری: فارسی از سرور (پیام خطا، عنوان اعلان، نام‌ها).

## ۴. احراز هویت
- ورود با موبایل (`09xxxxxxxxx`) + کد پیامکی ۴ رقمی؛ اعتبار کد ۲ دقیقه (تایمر اپ ~۶۰–۱۲۰ ثانیه)، حداکثر ۵ تلاش، محدودیت نرخ (شماره و IP و دستگاه).
- خروجی: `accessToken` کوتاه‌عمر (مثلاً ۱۵ دقیقه) + `refreshToken` چرخشی (با تشخیص استفاده‌ی مجدد). ۴۰۱ → اپ تلاش refresh، شکست → صفحه‌ی ورود.
- کاربر جدید → `isNewUser:true` → اپ نام را می‌گیرد (`PATCH /me`) و کد معرف اختیاری.
- حذف حساب: `DELETE /me`؛ غیرفعال‌سازی فوری، ناشناس‌سازی پس از مهلت قانونی (تصمیم لازم). سفارش‌های مالی حفظ می‌شوند.
- ارائه‌دهنده‌ی پیامک: تصمیم لازم (چند ارائه‌دهنده‌ی ایرانی هست؛ پیشنهاد: یک لایه‌ی انتزاعی `SmsProvider` با پشتیبان دوم).
- کد نمایشی ۱۲۳۴ فقط در محیط توسعه/استیج.

## ۵. مدل داده (هسته)
`city(id,name,center,polygon)` · `user(id,phone,name,cityId,referralCode,referredBy,deletedAt)` · `address(id,userId,title,fullText,plaque,unit,location,recipientName,recipientPhone)` · `restaurant(id,name,sub,type,tags,addr,location,coverUrl,hours/openH/closeH,etaMin,etaMax,fee,minOrder,allowExtras,allowCash,status)` · `category` · `food(id,restaurantId,title,desc,price,oldPrice,imageUrl,available)` · `option_group`/`option` (اجباری/اختیاری، min/max، `isExtra`، `priceDelta`) · `review(foodId,userId,stars,text)` · `favorite(userId,restaurantId)` · `promo(code,type,value,limits,validFrom/To,perUser,firstOrderOnly,restaurantIds)` · `campaign` · `order(id,number,userId,restaurantId,courierId,status,payMethod,paymentStatus,addressSnapshot,recipient,note,totals,etaMin,etaMax,placedAt…)` · `order_line(orderId,foodId,titleSnapshot,qty,unitPriceSnapshot,optionsSnapshot)` · `order_event(orderId,status,at,actor)` · `payment(orderId,provider,authority/trackId,amount,status,verifiedAt,ref)` · `rating(orderId,restaurantStars,courierStars,text)` · `report(orderId,typeId,text,photos)` · `notification` · `device(userId,channel,token)` · `partner_request` · `support_message` · `app_content(key,title,body,version)`.
قاعده‌ها: از قیمت/عنوان/آدرس هنگام سفارش **snapshot** گرفته شود؛ تغییر منو بعداً سفارش قدیمی را عوض نکند.

## ۶. ماشین وضعیت سفارش
```
(آنلاین)  PENDING_PAYMENT ──پرداخت تأییدشده──▶ PLACED
          PENDING_PAYMENT ──ناموفق/انصراف──▶ PAYMENT_FAILED  (سبد در اپ حفظ می‌شود)
          PENDING_PAYMENT ──مهلت (مثلاً ۱۵ دقیقه)──▶ EXPIRED
(نقدی)    ──────────────────────────────────▶ PLACED
PLACED ──رستوران می‌پذیرد (زمان آماده‌سازی ۱۰/۲۰/۳۰/دلخواه می‌تواند etaMin/etaMax را بازنویسی کند)──▶ ACCEPTED
PLACED ──رستوران رد می‌کند / بی‌پاسخ تا مهلت──▶ REJECTED  (بازپرداخت آنلاین)
PLACED ──مشتری لغو (فقط اینجا)──▶ CANCELED_BY_CUSTOMER (بازپرداخت آنلاین)
ACCEPTED ▶ PREPARING ▶ READY ▶ ON_THE_WAY (پیک برداشت) ▶ DELIVERED
```
نگاشت به StepBar اپ: PLACED=۰، ACCEPTED=۱، PREPARING/READY=۲، ON_THE_WAY=۳، DELIVERED=۴؛ وضعیت‌های لغو/رد/منقضی جدا نمایش داده می‌شوند.
هر تغییر: ثبت `order_event` + اعلان به مشتری (و به رستوران/پیک در صورت لزوم) + رویداد SSE. تغییر ETA هم اعلان می‌دهد.
تصمیم لازم: مهلت پذیرش رستوران، سیاست لغو پس از پذیرش، سیاست بازپرداخت، تخصیص پیک (خودکار/دستی/پیشنهادی).

## ۷. پرداخت
- روش‌ها: `online` (درگاه واسط: زیبال یا زرین‌پال — انتخاب نهایی هنوز نشده) و `cash` (فقط اگر `restaurant.allowCash`).
- جریان آنلاین: `POST /orders` → سفارش `PENDING_PAYMENT` + ایجاد تراکنش نزد درگاه → `redirectUrl` → کاربر پرداخت می‌کند → درگاه به `GET /payments/callback/{provider}` برمی‌گردد → **سرور حتماً verify می‌کند** (هرگز نتیجه‌ی query را باور نکنید) → سفارش `PLACED` → ریدایرکت به اپ (deep link اندروید / آدرس PWA) با `orderId` و `result`.
- ویژگی‌های لازم: lock روی سفارش و تأیید یک‌باره (ضد تکرار verify)، تطبیق مبلغ، لاگ کامل، مصالحه‌ی روزانه با گزارش درگاه، بازپرداخت.
- نقدی: سفارش بلافاصله `PLACED` با `paymentStatus=cash_due`؛ پیک وجه را دریافت می‌کند → `cash_collected` → تسویه‌ی پیک/رستوران (طراحی جداگانه؛ **تصمیم قطعی مالک: پیک وجه نقد را دریافت می‌کند**؛ اپ پیک بعداً با این قاعده ساخته می‌شود).
- لایه‌ی `PaymentProvider` با دو پیاده‌سازی تا بتوان درگاه را عوض کرد. جزئیات API هر درگاه را از مستندات رسمی خودشان بگیرید؛ در این سند چیزی از آن‌ها فرض نشده.
- کیف پول: تصمیم باز؛ فعلاً در قرارداد نیست.

## ۸. سایر قواعد کسب‌وکار
- **زمان تحویل** را رستوران تعیین می‌کند (`etaMin/etaMax`)؛ کاربر انتخاب نمی‌کند؛ زمان‌بندی (`allowScheduled`) منسوخ است.
- **حداقل سفارش و هزینه‌ی ارسال** از رستوران؛ `POST /checkout/quote` مرجع نهایی (جمع، تخفیف، موجودی، بسته بودن، روش‌های پرداخت مجاز) و `POST /orders` دوباره همان را بررسی کند (۴۰۹ `PRICE_CHANGED` اگر عوض شده).
- **کد تخفیف:** اعتبار تاریخ، سقف استفاده، هر کاربر، سفارش اول، رستوران خاص؛ پیام فارسی (مثل DOKOON10، FIRST20).
- **افزودنی‌ها:** اگر `allowExtras=false` گروه‌های `isExtra` را برنگردانید/نپذیرید.
- **محدوده‌ی سرویس:** ایجاد آدرس خارج از محدوده ۴۲۲ `OUT_OF_ZONE`.
- **نظرات:** هر غذا؛ فقط کاربر دارای سفارش تحویل‌شده (تصمیم لازم؛ پروتوتایپ محدودیتی ندارد) ؛ ضد اسپم.
- **امتیاز سفارش:** یک بار، فقط پس از `DELIVERED`.
- **لغو:** فقط در `PLACED`.
- **سفارش مجدد:** `GET /orders/{id}/reorder` قیمت/موجودی فعلی را برمی‌گرداند؛ سبد در کلاینت ساخته می‌شود.
- **دعوت دوستان/کد معرف:** پاداش و قواعد: تصمیم لازم.

## ۹. نقشه (نشان / بلد)
- هدف محصول: کاربر هنگام باز شدن نقشه بتواند **نشان یا بلد** را انتخاب کند؛ اگر یکی از آن‌ها خراب یا در دسترس نبود، دیگری جایگزین شود.
- سمت اپ: یک رابط `MapProvider` با دو پیاده‌سازی. `GET /app/config` فهرست `maps` و `defaultMap` را می‌دهد تا بتوان یکی را از سرور خاموش کرد.
- سمت بک‌اند: **مختصات (lat,lng) ملاک ذخیره‌اند، نه شناسه‌ی هیچ نقشه‌ای**؛ آدرس متنی هم نگه دارید. برای محدوده و فاصله از PostGIS خودتان استفاده کنید تا به هیچ ارائه‌دهنده‌ای وابسته نباشید. اگر geocoding/مسیریابی سمت سرور لازم شد، آن هم پشت یک رابط.
- لازم است: بررسی شرایط، قیمت و محدودیت SDK/API هر دو سرویس برای وب/PWA و اندروید و گرفتن کلید (تصمیم لازم؛ تأیید نشده).
- برای پیک: باز کردن مقصد در برنامه‌ی نشان/بلد (deep link) بدون وابستگی به SDK داخل اپ.

## ۱۰. اعلان‌ها
- انواع: وضعیت سفارش، تغییر ETA، پروموشن، اخبار (کلیدهای تنظیمات اپ: `notifyOrders/notifyPromos/notifyNews`).
- کانال‌ها: Push (اندروید)، Web Push (PWA؛ آیفون فقط iOS ≥ 16.4 و پس از افزودن به صفحه‌ی اصلی)، پیامک برای رویدادهای حیاتی (کد ورود؛ احتمالاً تأیید/لغو سفارش).
- **تصمیم لازم و ریسک:** سرویس‌های خارجی مثل FCM ممکن است در ایران مشکل داشته باشند. لایه‌ی `PushProvider` بسازید و راه‌حل جایگزین (سرویس پوش داخلی/اتصال سوکت دائمی با اپ باز/پیامک) را بررسی کنید. `POST /me/devices` کانال و توکن را ثبت می‌کند.
- ذخیره‌ی `notification` برای صفحه‌ی اعلان‌ها با `target:{screen,id}` برای deep link.

## ۱۱. امنیت و نکات غیرعملکردی
- TLS، رمزنگاری سکرت‌ها، محدودیت نرخ روی OTP/ورود/کد تخفیف/نظر/درخواست همکاری، اعتبارسنجی همه‌ی ورودی‌ها، کنترل دسترسی (کاربر فقط داده‌ی خودش)، لاگ حسابرسی روی عملیات مالی.
- آپلود: نوع/اندازه (≤ ۵MB)، بازپردازش تصویر. دادهٔ شخصی (موبایل، آدرس) فقط تا حد لازم در لاگ.
- عملکرد: لیست‌ها صفحه‌بندی‌شده؛ تصاویر در اندازه‌های متعدد/CDN؛ هدف زمان پاسخ و بودجه‌ی خطا را با هم تعیین کنید.
- مشاهده‌پذیری: لاگ ساختاریافته، شناسه‌ی درخواست، هشدار روی خطای پرداخت.
- محیط‌ها: dev / staging / production با داده و کلید جدا؛ پروتوتایپ با داده‌ی نمونه‌ی مستند کار می‌کند.

## ۱۲. بقیه‌ی APIها (هنوز مشخصات کامل ندارند)
- **رستوران:** ورود، فهرست زنده‌ی سفارش‌ها (پذیرش/رد با زمان ۱۰/۲۰/۳۰/دلخواه، آماده)، مدیریت منو/گزینه‌ها/موجودی، ساعت کاری/باز-بسته، `etaMin/etaMax`، `allowExtras`، `allowCash`، گزارش و تسویه.
- **پیک:** ورود، آنلاین/آفلاین، پیشنهاد/قبول سفارش، مسیر و تحویل، ثبت دریافت وجه نقد، ارسال لوکیشن (اندروید در پس‌زمینه)، درآمد و تسویه.
- **ادمین:** کاربران، رستوران‌ها (تأیید درخواست همکاری)، پیک‌ها، سفارش‌ها، پرداخت/بازپرداخت/نقدی، کمپین، تخفیف، محتوا (درباره/قوانین/FAQ/شبکه‌ها)، شهر و محدوده، تنظیمات اپ (`/app/config`).
- این‌ها را بعد از تأیید قرارداد مشتری به همین شکل (OpenAPI) می‌نویسیم.

## ۱۳. روش همزمان‌کاری فرانت و بک
1. `dokoon-openapi.yaml` تنها منبع قرارداد است؛ هر تغییر با Pull Request روی همین فایل، با توضیح و شماره‌ی نسخه. تغییر شکننده → `/v2` یا هماهنگی کتبی.
2. فرانت با **mock server** از روی همین فایل کار می‌کند (مثلاً Prism یا MSW)، بدون انتظار برای بک‌اند: `prism mock dokoon-openapi.yaml`.
3. بک‌اند از همین فایل تست قرارداد (contract test) می‌سازد تا انحراف از قرارداد زود پیدا شود.
4. هر هفته یک بار هماهنگی: فهرست تغییرات قرارداد، موارد «تصمیم لازم»، و تست یکپارچه روی استیج.
5. ترتیب پیشنهادی ساخت بک‌اند: (الف) auth + config + شهرها + آدرس‌ها، (ب) رستوران/منو/جستجو/خانه، (ج) quote + سفارش نقدی + وضعیت‌ها، (د) پرداخت آنلاین، (ه) اعلان‌ها و SSE، (و) نظرات/علاقه‌مندی/محتوا/پشتیبانی، (ز) ادمین و اپ رستوران/پیک.

## ۱۴. فهرست «تصمیم لازم»
میزبانی/دامنه · ارائه‌دهنده‌ی پیامک · پوش در ایران · درگاه (زیبال/زرین‌پال) و نرخ/تسویه · نقشه (شرایط نشان و بلد) · سیاست لغو/بازپرداخت · مهلت پذیرش رستوران · تخصیص پیک · تسویه‌ی نقدی · محدودیت نظر · پاداش دعوت · مدت نگهداری داده‌ی حذف‌شده · دسترسی مهمان (مرور بدون ورود).
